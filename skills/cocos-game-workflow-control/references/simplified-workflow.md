# 简化工作流视图

本文件是面向用户的工作流入口。它把项目展示为六个阶段、把单场景视觉生命周期展示为四步，帮助用户理解当前任务和下一项工作。普通任务直接依据用户当前指令推进，任务内方案、路径、资源清单和测试范围可随实施更新；不要求独立授权记录或 F0 授权有效门。它只是只读投影，不写回 Work Item，也不替代 `globalState`、G0-G3、V0/V1/V2/V3/V4、A0-A6、F0-F4、审批账本、证据哈希或任何 Schema。

## 图片优先的确认方式

除帧动画方案确认外，图片任务按“内部整理 → 直接展示真实图片或预览 → 用户确认 → 继续”推进。分析、提示词、技术 JSON、来源和确认回执由代理维护，不要求用户先阅读或确认文字提案；用户主动索要时再展开。实际图片确认只记录一次，不再要求确认文字复述。

帧动画在动作方案完成后、制作真实素材前，主动按[设计理念说明](../../cocos-frame-animation/references/intent-driven-design.md#方案完成后阐述设计理念)说明目标感受及动作与节奏产生这种感受的依据；说明后暂停，等待用户明确确认当前动作方案。收到确认后才在已有授权范围推进素材制作和具体实现，真实素材仍须人工确认。

游戏画面中的内容按[游戏内文案](../../cocos-game-ui-layout/references/game-copy.md)贯穿策划、效果图和实现：内部规格分开保存，图片/图标/数字/符号优先，文字只补充必要语义；生成前指定可见文字范围，正式场景沿用同一表达，不把策划详细说明复制到画面。此规则不影响拆解标注、流程说明或 V2 布局审阅。

| 任务 | 用户看到的候选 | 内部处理 |
| --- | --- | --- |
| 场景目标 | 效果图或宿主上下文预览 | 明确需求与基线按 AUTO 推导；真实方向、玩法或结构歧义才询问 |
| 拆解 | 编号拆解 PNG 与图中简短说明 | 先完成状态分析、组件清单、生产路线和技术 JSON，直接产图 |
| 布局 | 拆解确认后的布局 PNG 或审阅页 | 自动维护父子关系和对齐决策，不先请求文字方案确认 |
| 静态资源 | 批量图片画廊或可放大的参考/输出对照 | 保留独立资产与工程检查，文字只列失败、缺项和待处理项 |
| 返修 | 参考、修改前与修改后对照 | 已确认目标范围内直接修复，不单独确认文字修复方案 |
| 动画 | 动作方案与设计理念说明；确认后展示真实视频、首尾/关键帧及序列预览 | 先说明目标感受和动作依据，等待用户明确确认当前方案后再制作；真实素材仍按路线人工验收 |

拆解确认后再生成布局，两个图片确认仍分别保留；图片动画只在实际父图确认后制作依赖帧，真实视频验收后才能抽帧。图片、预览与观看效果由用户人工检查，代理不能代写通过。缺少素材或工具时说明真实缺口，不用文字方案、占位图或机器 PASS 冒充视觉候选。费用、外部写入、真机与发布仍按已有明确操作授权执行。

## 六阶段项目视图

| 阶段 ID | 用户阶段 | 聚合产物 | 内部映射 |
| --- | --- | --- | --- |
| `requirements-scope` | 需求与范围 | Work Item 摘要、用户目标、范围、基线和验收清单 | `INTAKE` |
| `global-baseline` | 全局基线 | GDD、TDD、全局视觉基线、任务范围和全局选择证据 | `G0`、`BASELINE`、`PROPOSAL`、`REVIEW` |
| `foundation-engineering` | 基础工程 | foundation-only 实施包、`SHARED`/`MODULE` 基础代码和验证证据 | 仅含 `SHARED`/`MODULE` 的实施包；纯工程包可在全局选图前实施，视觉依赖包仍受全局基线门约束 |
| `scene-production` | 场景与弹窗生产 | 场景或独立弹窗的规格、V2 拆解方案、V3 正式资源、V4 正式还原与运行验收证据 | `V0`、`V1`、`V2`、`V3`、`V4`，或独立包含 `SCENE`/`DISPLAY_LAYER` 的实施包 |
| `global-integration-validation` | 全局集成验证 | 跨场景集成候选、导航/存档/音频/性能/响应式回归和联合证据 | `G2`、`INTEGRATING`，或纯 `INTEGRATION` 实施包 |
| `release` | 发布 | 独立发布 Work Item、可复现发布包、平台/合规/回滚资料和精确审批回执 | `G3`、`RELEASE_APPROVAL_REQUIRED`、`RELEASING` 或发布 Work Item |

判断有冲突时按“发布 → 集成 → foundation-only → 场景 → 需求/基线”的固定顺序检查；包内单元类型跨越不相容阶段、视觉阶段声明冲突或无法识别时返回 `unknown`，同时保留内部 `stage`，不伪造进度。foundation-only 仅按单元类型识别范围，是否等待全局选图由包内视觉合同/资产生产字段和正式视觉行为决定。

基础工程阶段必须按[基础显示约束](../../cocos-game-orchestrator/references/game-implementation.md#基础显示约束)完成游戏全屏显示；目标包含 Android 时，启动首帧、启动画面切换及运行全程均不得显示窗口标题栏或 ActionBar，并在后台返回和窗口焦点恢复后保持沉浸式全屏。此项属于基础平台能力，不等待场景视觉生产；无实际运行证据的验收项须明确标记未验证，真机验收仍需用户明确授权。

音频生命周期也在基础工程阶段完成：按[后台暂停与恢复约束](../../cocos-game-audio/SKILL.md#后台暂停与恢复约束)，进入后台暂停播放，返回前台后从原位置继续；手动暂停、停止或销毁的音频不自动恢复，后台新请求不补播。

基础工程同时按[游戏项目目录规范](../../cocos-game-architecture/references/project-structure.md)和[产物存放与证据边界](../../cocos-game-architecture/references/artifact-storage.md)建立实际需要的目录：入口与基础服务分层，场景内部按功能聚合，平台适配、独立显示层、正式资源、源素材、测试和生成产物分清归属；路径与所有权在 TDD 和实施包中明确，不预建空壳目录。根级 `evidence/<workItemId>/reviews/` 与 `validation/` 用于人工作业审阅和验证，机器 `evidenceRoot` 按 Work Item 实际配置使用，受限字段不得填写该根目录以外的路径。

## 四步单场景视图

| 步骤 ID | 用户步骤 | 内部阶段 | 关键产物 |
| --- | --- | --- | --- |
| `scene-definition` | 场景定义 | `V0`/`V1` | 场景功能契约、scene master/reference target、宿主上下文图、视觉合同、布局/容差合同和初步还原草案 |
| `direction-confirmation` | 拆解确认 | `V2` | 拆解图、技术 JSON、coverage、component×state、父子/停靠/对齐/显示层事实和生产方案 |
| `production-ready` | 正式资源验收 | `V3` | 已验收正式资源、组件状态、资产文件身份与生产记录 |
| `formal-implementation-runtime-validation` | 正式还原与运行验收 | `V4` | 直接消费 V2 拆解/布局与 V3 正式资源的 `SCENE`/`DISPLAY_LAYER` 实现、运行轨迹、视觉/功能联合验收、响应式和性能证据 |

V2→V3→V4 在同一场景 Work Item 内通过显式阶段入口推进。每个入口默认写入 `in-progress`。V3 正式资源验收和 V2 证据闭合后，直接激活 V4 正式实施；V4 运行态证据闭合后提交 `v4-runtime-integration-candidate`。视图直接消费真实视觉阶段，实施包状态不能跳过 V2/V3 前置。

V4 在正式 Scene 中组合 V2 结构和 V3 资源，按实际运行画面调整布局、资源呈现和动态状态；布局或素材偏差由其真实来源所属阶段修复，并对受影响的正式运行证据复验。用户人工检查当前实际画面，机器检查不代替视觉验收。具体见[正式场景视觉还原与校准](../../cocos-game-asset-integration/references/visual-alignment-authoring.md)。

场景路线还需在 V1 确定[显示对象默认中心锚点与渲染分层](../../cocos-game-ui-layout/references/display-object-layering.md)：对象例外、背景/世界/特效/HUD/瞬态层顺序和每层的坐标、输入、生命周期归属。V2 固化布局与显示层合同，V4 在实际场景中用遮挡、命中和恢复轨迹验证；渲染分层不新增全局阶段，也不把普通世界层误记为独立 `DISPLAY_LAYER` Work Item。

### 序列帧路线映射

通用帧动画沿用全局状态机，按[分类入口](../../cocos-frame-animation/SKILL.md#分类入口)选择用途，默认视频抽帧；图片递归补帧仅在用户明确选择或确认切换时启用。V2 内部完成动作分析、时间轴和区域/分辨率方案，说明设计理念后等待用户明确确认当前动作方案；确认后才写提示词并在已有授权内制作真实候选，只有事件、时长或行为边界有决定性歧义时询问。视频分辨率与条数按[区域规划](../../cocos-frame-animation/references/region-planning.md)选择并遵守预算；图片默认 768p，确需 2K 时在已有工具与预算授权内直接选择，新增费用或超出授权才询问。V3 人工验收实际最终抽帧视频后才抽帧，图片首尾、必要关键帧和递归帧在真实父图确认后推进；最后验收完整真实序列。仅确认文字参数不能证明表现或衔接通过，内部记录由代理维护。图集、来源、时间映射、声音及 V4 Cocos 接入见[通用帧动画接入合同](../../cocos-frame-animation/references/workflow-integration.md)。

例如，V2 完成后可在同一 Work Item 上执行：

```powershell
node <skill-dir>/scripts/workflow-control.mjs transition --work-item <work-item> --to REVIEW --visual-stage V3
```

V3 证据闭合后直接进入 V4 并激活正式实施包；V4 实施及运行证据闭合后提交 `--visual-stage-state v4-runtime-integration-candidate`，再进入 `VALIDATING → PASSED → COMPLETE`。阶段入口使用的全局状态与命令参数以控制面当前校验结果为准，禁止直接改状态字段跨过确认门。

没有可识别的 `V0`、`V1`、`V2`、`V3` 或 `V4` 声明时，生产阶段仍可显示为“场景与弹窗生产”，但 `sceneStepId` 和 `sceneStepLabel` 必须为 `null`；这表示缺少可投影的步骤，不表示任何视觉门已通过。

## CLI 输出

`run` 连续推进已满足条件的安全内部状态，每步重新校验并在 `changed` 中记录实际迁移。进入 `IMPLEMENTING`、缺少包/审计/证据、遇到用户决定或操作批准时停止；它不执行实施或测试，也不选择视觉阶段或 `RETURN`。视觉阶段仍使用上述显式 `transition` 入口，底层 `advance` 保持单步诊断语义。

`run`、`check`、`status` 的 JSON 顶层字段保持 `status`、`stage`、`changed`、`blocking`、`next`、`metadata` 不变。`stage` 继续使用内部 `${stageId}/${globalState}`；`metadata.workflowView` 只增加稳定的 `phaseId`、`phaseLabel`、`sceneStepId`、`sceneStepLabel` 四个展示字段。

默认文本优先显示简化阶段，例如：

```text
阶段：场景与弹窗生产 · 拆解确认
下一步：完成当前待执行单元
```

下一步文案使用用户可理解的聚合称呼，例如“更新当前阶段实施包”“完成当前待执行单元”“记录当前候选变更审计”“提交当前候选验证证据”“准备正式集成审批”。这些文案只改变显示，不改变原有条件、状态迁移或门禁逻辑。测试等级先按改动风险推荐并说明理由、覆盖和命令，再自动执行适用等级，不等待人工选择。

## 门禁边界

简化视图不改变关键门：V2 冻结拆解与目标布局，V3 完成正式资源验收，V4 直接在正式场景中实现、校准并完成真实运行态联合验收；G2 只验证完整候选，G3 仍必须是独立发布 Work Item；涉及外部写入、付费、真机、破坏性或外部删除、发布副作用的 A4-A6 操作仍按明确对象和影响逐项审批，无副作用本地 A4 不因等级标签额外审批；F0-F4、证据文件路径与实际内容仍由控制面校验，SHA 不参与验收。普通视觉验证默认使用 `visual_validation.mode=usability`，允许位置、尺寸、边距和换行有合理偏差，重点检查越界、裁切、遮挡、可读性和交互；只有明确精确需求时才使用 `exact`，启用像素容差或全视口/全状态矩阵。缺少非关键元数据优先提醒并自动补齐，局部修改只重验受影响范围。
