# 汁水感工作流接入

## 组织决策

采用“独立领域 Skill + 现有流程按需引用”：[cocos-game-juice](../SKILL.md)提供跨视觉、声音、镜头、时间和交互的专门设计入口，[完整指南](design-guide.md)是详细规则的单一来源；总控、策划、玩法、UI、资源、动画、音频和 QA 保持现有所有权。

不把完整指南塞进所有 Skill 的正文，也不把汁水感变成新阶段、全局状态、审批门或运行时必需服务。这里的独立入口允许用户直接要求“增强打击感”“优化卡牌结算反馈”“审查高频效果”；各领域仍在当前工作项内交付，不因调用它就创建第二个场景任务。

现有[游戏感质量门](../../cocos-game-asset-integration/references/game-feel-quality-gate.md)负责游戏感领域质量，[美术体验契约](../../cocos-game-asset-integration/references/art-quality-contract.md)负责主题、受众和观看体验，[玩法视觉契约](../../cocos-game-asset-integration/references/gameplay-visual-contract.md)负责动态可读性。本指南补事件设计和执行细节，不复制或修改上述质量门。

## 启用条件与范围

| 情况 | 接入方式 |
| --- | --- |
| 用户明确要求汁水、打击感、动效、声音同步或反馈审查 | 在指定事件和模块内调用本 Skill |
| 当前核心行为已有反馈范围，但成功/拒绝/中断等结果不清楚 | 补齐该行为的语义与最小确认，不扩大到整局润色 |
| 新游戏的 GDD 正在定义核心循环 | 在既有反馈意图中引用类型矩阵和关键事件模板 |
| 当前任务只有纯布局、静态美术或规则调整，反馈不受影响 | 不启用专项，不加载全指南 |
| 已冻结目标与拟增加效果发生冲突 | 查明当前授权和真实影响；只对仍未决的实质取舍请求决定 |
| 局部参数或资源方案调整 | 更新受影响计划和证据；不重复无关确认 |

## 现有阶段映射

| 阶段 | 本领域补充的事实 | 继续沿用的边界 |
| --- | --- | --- |
| 需求与范围 | 事件范围、体验目标、必要确认、非目标 | 当前 Work Item 与 GDD，避免全量润色 |
| 全局基线 | 反馈语言及常态/操作/峰值意图 | brief、静态基线与现有人工质量结果；静态通过不证明动态通过 |
| 基础工程 | 当前需求确实需要的公共事件、时间、音频、生命周期能力 | foundation-only 仅场景无关能力；优先复用，不提前实施正式场景反馈 |
| V1 场景定义 | 输入、规则、反馈语义、关键事件、成功/失败、预算与边界 | 现有规格和适用灰盒；帧动画不另做几何样片 |
| V2 拆解与布局 | 状态、表现节点、动效空间、资源与程序逻辑职责、动画事件点 | 既有拆解与布局确认、生产路线；不增加一次汁水确认 |
| V3 资源验收 | 所需素材、音效变体、锚点、帧事件、实际资源登记 | 正式素材通过既有资源门；程序效果不等于可以替代冻结位图 |
| V4 正式场景 | 同屏层级、基本组合与偏移是否符合目标 | 结合真实运行验收；静态画面不证明时序和手感 |
| V4 正式还原与运行验收 | 规则事件驱动反馈、重复/并发/取消、清理、真实动态证据 | 正式代码、资源与布局前置；程序结果和人工显示/手感分别记录 |
| 全局集成验证 | 跨场景音频、设置、共享预算、恢复、完整循环 | 只按实际受影响范围集成，不重做已有效的局部证据 |
| 发布 | 当前候选的设置、资源资格及已完成验收 | 发布仍是既有独立工作项，不由本 Skill 执行 |

不要求已有项目从 V1 重走全链。由控制面依据真实影响选择当前阶段；纯参数修复通常原地修复并复验，只有上游规则、结构或正式资源事实改变时才返回最早受影响阶段。

## 领域所有权

| 领域 | 负责 | 不由汁水 Skill 接管 |
| --- | --- | --- |
| 制作策划 | 反馈范围、体验目标、GDD 与功能验收 | 产品方向与玩法选择 |
| 编排 | 依赖、任务包、文件所有权、证据交接 | 全局状态与审批账本仍归控制面 |
| 架构 | 确实需要的事件接口、时间/生命周期边界和模块依赖 | 局部效果不强制新增公共框架 |
| 玩法 | 规则、状态、碰撞、结算、事件触发、实际击退 | 表现动画不决定扣血、费用、库存或胜负 |
| 数值 | 确有规则影响的顿帧、硬直、吸附、输入容错、经济反馈 | 不把纯粒子参数混进经济或战斗模型 |
| UI | 布局、焦点表现、布局坐标合同与可读文字 | 玩法保留交互代码，架构维护跨模块坐标；反馈不覆盖基础布局或另写坐标公式 |
| 美术接入 | 资源生产路线、登记、外观与集成 | 冻结素材不得被未批准的程序简化效果替代 |
| 帧动画 | 动作时间轴、素材、关键帧事件与人工验收 | 局部 Tween 不强制升级成帧动画生产 |
| 音频 | 声音分组、变奏、混音、实例、解锁和后台生命周期 | 后台暂停恢复继续引用音频 Skill 的唯一详细约束 |
| QA | 事件、参数、功能、清理、性能和可复现材料 | 显示、舒适和手感由实际人工验收确认 |

日常粒子、飘字、受击形变不会仅因“瞬态”就自动成为 DISPLAY_LAYER。modal/popup 等界面层按[现有显示层规则](../../cocos-game-workflow-control/references/control-model.md#弹窗工作项与场景解耦)独立规划；反馈效果按当前场景、组件与模块所有权处理。

## 工件与追踪

优先在项目现有 GDD、TDD、visual-design、qa-plan 及事件配置中维护事实。需要专门文档时可用 `docs/game-feel.md`，只把事件规格和相关索引集中起来；它不是新的全局状态文件，也不要求所有项目创建。

建议的追踪关系：用户目标 → 关键事件 → 规则/表现所有者 → 实际配置与资源 → 测试和动态材料 → 人工结果。工件之间用事件 ID 与路径引用，不复制多份参数正文。ID 是项目内部标识，不写入玩家界面。

实施包仍使用现有 Schema 支持的规格引用、所有权、输入、输出及验证字段。不要擅自添加强制 `juiceStage`、`juiceApproved` 等字段，也不把领域事件表伪装成已被控制器验证的机器合同。未新增确定性验证器时，边界一致性由审查和现有检查负责。

## 验证与交接

设计文档一般按 T0 检查范围、链接、语义与待决事项；技能入口或引用变动可按 T1 运行仓库 lint 和技能结构校验。实现任务按实际影响推荐 T1-T3，并在推荐理由、覆盖、拟执行命令后自动执行，失败修复后复验。

程序验证只宣称实际检查过的事件和边界。动态材料沿用现有 `normal-play`、`repeated-feedback`、`event-peak`、`overlap-peak` 等适用情境及实际候选身份，不引入旧 `human_review` 字段或新确认节点。用户人工检查结果按现有验收材料保存；未观看写未验证。启动验证服务前复用同项目健康实例，不自动真机验收。

交接最少包含：当前事件范围、实际改动路径与符号、规则影响、执行的验证与结果、动态材料和人工状态、未决项。持续修复只重验受影响事实；不要以修改规格降低未完成要求，也不因内部表现实现调整追补历史合同。

## 最小接入示例

用户要求“给当前卡牌出牌增加反馈”时：

1. 制作/玩法确认已有费用、合法目标、提交与结算规则，不新增卡牌机制。
2. 用指南模板记录选择、预览、提交、拒绝、实际结算和取消；沿用当前场景或显示层工作项。
3. UI 确定基础布局与视觉偏移，玩法维护交互代码；音频选择已有确认/拒绝声音；仅缺素材时进入既有资源路线。
4. 在当前允许阶段实现，规则层确认后驱动表现，避免在 Tween 完成回调中扣费。
5. 定向验证重复提交、目标消失、取消、切场景与静音；提供正常、拒绝和联动片段供人工检查。
6. 回到控制面记录实际完成与未验证项，不增设汁水审批或重新确认无关布局。
