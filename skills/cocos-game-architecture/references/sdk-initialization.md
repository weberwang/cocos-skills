# SDK 统一初始化

项目实际采用的第三方 SDK 统一由 `assets/scripts/platform/initialize-sdks.ts` 管理。唯一应用装配入口调用该模块并分别投递 SDK 任务；应用装配组件可以由启动场景承载，但启动场景不负责具体场景业务初始化。没有采用 SDK 时不创建占位文件，也不因本规范增加 SDK 或依赖。

## 唯一入口与职责

- 入口只投递各 SDK 的独立任务并立即返回，不等待整批初始化。Creator 首帧、Boot 和场景启动不等待 SDK 初始化批次；不得使用等待全部 SDK 的 Promise 门、全局 `allSdksReady` 或其他启动屏障。
- 所有已采用 SDK 的配置校验、平台分流、初始化调用、真实完成回调、幂等状态、操作身份与初始化重试由该文件集中维护。每个 SDK 使用独立状态和私有任务；不得只放注册表，再把初始化或恢复逻辑散落到广告服务、隐私模块、Scene、Component 或平台入口。
- 公共类型、纯配置、原生插件安装和必要宿主配置继续归属原有文件。平台适配器可以封装原生 API 调用细节，但不得在构造函数、模块导入或场景生命周期中自行启动 SDK，也不得持有第二份初始化状态或重试器。
- 广告加载/展示、支付、登录界面、埋点业务和隐私交互仍由各自业务模块管理。SDK 就绪后的广告位加载恢复等运行任务由广告服务持有；业务模块通过已注入的能力接口读取结果或请求对应 SDK 的单独重试。
- SDK 导入不得在模块顶层产生初始化副作用。可选 SDK 的动态加载或调用失败必须在该 SDK 自己的任务中捕获，不得影响共享入口或其他 SDK 任务。

## 独立启动与真实前置

1. 应用装配入口对每个已启用且平台支持的 SDK 分别投递任务。一个 SDK 的配置错误、动态导入失败、同步异常、Promise 拒绝、初始化失败、重试或永不回调，都不能阻止其他 SDK 任务发起。每项任务独立处理拒绝并记录自身结果。
2. 禁止跨 SDK 的 `await A(); B()`、Promise 链、依赖启动图、等待全部 SDK 完成的 `Promise.all` 门，或在 A 的成功回调中才发起 B。全部独立任务投递后可以使用 `Promise.allSettled` 汇总诊断，但汇总结果不能作为游戏启动或其他 SDK 的前置。
3. 每个 SDK 只等待自身真实需要的平台、配置、宿主或桥接条件。条件未满足时只保留该 SDK 的待初始化意图，不让其他 SDK 或首帧陪同等待。不得借登录、隐私界面、广告加载、正式场景或 UI 就绪建立项目级启动屏障。
4. 不得绕过锁定版本官方明确要求的真实前置。如果官方前置使某 SDK 暂时无法独立初始化，记录 SDK、锁定版本、具体前置和来源，只将该 SDK 标记为受限；继续投递其他无关任务，不伪造初始化成功，也不建立全局等待。
5. 广告、支付或跟踪等实际业务动作仍由对应合同检查 SDK 就绪、真实隐私状态和操作条件。解耦初始化不授权提前请求广告或执行其他业务动作；能力未就绪时返回该能力自己的状态。

## 幂等、回调与失败隔离

- 同一应用生命周期、同一有效配置下，每个 SDK 只发起一次初始化；重复入口复用该 SDK 正在进行的请求或已完成状态，不重启其他 SDK。配置替换、禁用或销毁时只使该 SDK 的旧操作和回调失效；迟到或重复回调不得覆盖新状态。
- 只有 SDK 的真实完成回调或官方明确的就绪信号才能确认初始化成功。请求受理、初始化函数返回或其他 SDK 成功都不能代替完成事实；超时本身也不能伪造 SDK 失败或成功。
- 每个 SDK 独立持有初始化请求标识、错误分类、失败次数、deadline 和至多一个恢复 timer。重试只恢复目标 SDK，不重跑其他 SDK。配置错误、平台不支持或官方前置未满足时保留清晰阻断，修正前不盲目循环重试。
- SDK 特有退避、生命周期与条件恢复以该 SDK 合同为准；初始化恢复不得与广告位加载、支付交易或其他运行任务共用计数或 timer。
- 诊断只记录 SDK 身份、平台、阶段和脱敏错误分类；不记录 SDK key、凭据、设备标识或完整原生异常。

## MAX 与 AppsFlyer

MAX 初始化任务和真实隐私状态处理由不同模块分别投递，互不等待。MAX 调用及其完成回调属于 MAX 自己的初始化分支；CMP/Google UMP/ATT 的交互与授权状态由独立隐私模块处理。

- 新 MAX 实例首次实际初始化前，按[广告合同](../../cocos-game-ad-integration/references/applovin-max-contract.md#max-隐私配置与初始化时序)调用锁定插件所支持的 `setHasUserConsent(false)`；同实例的初始化重试复用已确定配置，不再次写回 `false` 覆盖后续真实隐私更新。MAX 内建 Terms and Privacy Policy Flow 必须通过已支持的宿主或原生配置在初始化前显式关闭，并核验最终生效配置。
- `hasUserConsent=false` 是 MAX 初始化配置，不是用户同意或拒绝回执，也不代表广告不可用。它本身不阻断 MAX 初始化、广告请求或加载恢复；广告业务仍按其他真实适用的 CMP/TCF、地区、宿主和网络条件处理。
- 项目采用 AppsFlyer 时，在同一文件登记独立初始化任务。按锁定插件官方语义处理 AppsFlyer 自身的 session-ready 条件；不得等待 MAX、广告加载或归因回调，MAX 也不得等待 AppsFlyer。配置、状态和失败恢复只影响 AppsFlyer。
- 官方真实前置若与独立初始化目标冲突，按“独立启动与真实前置”仅报告并阻断对应 SDK；不得谎报 CMP/ATT 结果、套用其他框架 API或扩展为全局等待。

## 交付与验证

在 TDD 与实施包中记录采用的 SDK、目标平台与配置来源、真实前置、完成信号、状态所有者、失败分类、初始化重试所有者及业务使用边界。没有实际需求时不安装未采用的 SDK。

目标项目的定向验证覆盖：两个 SDK 独立投递；单个 SDK 抛错、拒绝、失败或不回调时其他 SDK与首帧不受阻；重复入口、配置切换和迟到回调；平台不支持及 SDK 自身官方前置；单 SDK 重试不重跑其他 SDK；广告运行期重试与 SDK 初始化恢复互相隔离。采用 MAX/AppsFlyer 时还需核验 MAX 内建流程关闭、首次设置 `false` 后收到实际初始化回调，以及 AppsFlyer 按自身官方条件实际启动。

本仓库只交付 Skill 指导文件时执行文档、链接及仓库回归检查；不得将这些检查描述为真实 SDK 集成通过，也不要求真实 SDK 调用、真机、外部控制台配置或发布。
