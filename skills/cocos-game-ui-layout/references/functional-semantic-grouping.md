# 功能语义分组约束

适用于 V2 的效果图拆解与后置布局。先确认功能归属和共同职责，再分别记录实际父子关系与定位参照。父子关系表达功能、共同状态/交互/生命周期或真实布局管理归属；定位参照表达位置计算依据。两者可以不同，不能为了表示一般位置依赖而把元素强行改成直接父子，也不能根据元素类型、最近距离或最小包含矩形自动增加父容器。一个底板节点可以同时是图片渲染节点和功能/布局容器：显式使用 `element_type: container`、`render_kind: sprite`，并以 `semantic_grouping.kind: component` 或 `region` 声明容器语义；保留该节点自身的 `component_id`、`placement_id` 与图片资产身份，不复制成“空根 + 底板叶子”。

屏幕节点还须记录父容器职责、布局所有者、尺寸/溢出/安全区和输入策略。字段及 Cocos 根节点、空容器与 V1/V2/V3/V4 组织规则详见[Cocos UI 节点组织](layout-hierarchy.md)；`ui_layout` 不取代本文件定义的语义归属。

## 判断原则

- 全屏 UI 以场景逻辑尺寸为根参照；有底板弹窗以底板对应功能容器的尺寸为内容参照，底板容器本身相对场景定位；无底板弹窗以宿主场景逻辑尺寸为参照。先按[场景与弹窗尺寸参照](layout-hierarchy.md#场景与弹窗尺寸参照)确认边界，再建立内部功能归属与布局关系；弹窗底板是功能面板，不是全屏背景，简单结构允许底板 Sprite 同节点兼任组件容器。
- `parent_element_id` 表达元素实际归属的父容器：适用于共同功能、共同状态/交互/生命周期控制，或确实负责管理子项布局的关系。父级是 `region`/`component` 容器或稳定根 `viewport`/`safe-area`。位置依赖本身不足以建立直接父子关系；依赖方仍归属其真实功能容器，可通过可选 `ui_layout.position_reference_id` 指定位置参照。简单的“底板 + 图标 + 文本”优先把底板图像节点本身作为 `component` 根，图标与文本作为其兄弟子项；文本按真实设计相对底板或图标定位，不强制挂在图标下。纯结构容器若额外包裹一个可用底板及内容，必须在 `ui_layout.independent_container_reason` 写明该层的独立职责；“分组”“包含子项”不构成理由。
- `ui_layout.position_reference_id` 省略时，定位参照默认为实际父级。显式参照可指向同一 scene/state、同一坐标空间中的兄弟节点、祖先节点、`viewport` 或 `safe-area`；允许引用叶子节点，但全屏装饰背景不能作为其他节点的定位参照。缺失、自指，或把父子边与参照边合并后形成环，均为无效结构。声明了独立参照时，`ui_layout.grouping_basis` 必须包含 `POSITION`。
- 不要求父容器几何完整包住所有子项。角标、关闭按钮、光效等可以在真实父级范围外显式声明 `ui_layout.visual_overflow: {reason: "..."}`，其中 `reason` 必须是非空中文说明。该声明允许子项越出非根父框，父框仍按自身职责取尺寸，不得为了包含突出部件而扩大；viewport、safe-area 和目标画布边界仍须满足，裁切、安全区与交互验收也仍然有效。
- 信息分组由表达目标决定：共同表达同一信息或功能、共同状态或交互的内容归属对应组件。图标和文字即使互不依赖定位，也可以同属一个按钮组件并作为同级子项；需要文字相对图标定位时仍使用独立定位参照，不因此把文字改成图标的子项。
- 区域容器可以组织多个功能组件。例如侧栏包含多个入口组件，各入口再包含自己的图标与文字；不能把所有入口的图标、文字按类型合并成一个新容器。
- 原子资源身份与布局归属分离。不同入口可以复用同一图标资源，但每个可见实例仍属于自己的入口；不能仅凭相同资源 ID 合并容器。
- 不影响功能时，按[完整拆解与视觉显著性](../../cocos-game-asset-integration/references/asset-production-routes.md#完整拆解与视觉显著性)完整登记合成位图中可分离的文字、图标、底板、色彩填充等部件；系统文本和原生填充也保留为独立拆解项。拆开视觉来源不拆散功能归属，交互、状态联动、动态更新与本地化仍由对应组件协调。
- 几何包含、距离、显示层更低或图片尺寸更大只用于辅助观察与验证，不决定父级、参照或分组。全屏背景、阴影、光晕等装饰图片不作为内容的功能父框。先确认职责与归属，再测量 bounds、选择定位参照并计算偏移；不得为了类型分类、几何包含或校验通过而增加包装层。
- 独立标题、背景、装饰或不可可靠分离的完整品牌美术可以直接属于区域或根，不强制创建只有一个元素的容器；完整美术不能成为省略可独立部件的理由，整体保留时记录不可分离或分离会损伤既定视觉意图的原因。无需强制每个组件同时拥有图标、底板和文字。
- 空容器必须有已确认的用途与理由，不得把留白当作空容器。纯结构容器不声明 `render_kind`，也不生成 `sprite_geometry`；底板节点即使带有子项，仍按自己的图片身份声明 Sprite 尺寸计划。分组本身不改变已确认元素的身份、尺寸或顺序；布局阶段可依据显式的[居中策略与组合定位](center-alignment.md)平移单个元素或整组，父级或定位参照的整体位移也沿依赖关系传播到其子项和定位节点、保持原有相对间距，且不得改写 proposal 中的原始测量 bounds。普通固定视觉图片（包括普通 RAW 底板）输出 `sprite_geometry={type:'SIMPLE',size_mode:'RAW',content_size:null}`；只有已冻结九宫格的图片计划自定义显示尺寸。纯结构容器、文字和命中区域不声明 Sprite 尺寸计划；尺寸边界见[Cocos 适配器](cocos-adapter.md#图片原尺寸与九宫格尺寸)。

### 简单底板组件

以下三节点结构足以表达常见展示组件。底板既是可见图片，也是功能根；图标和文字可以相对底板布局，或让文字相对图标定位。底板的子项数量不会使它变成纯结构容器，也不会改变普通底板的 RAW 原尺寸。

```text
ResourceDisplay [element_type=container, render_kind=sprite, kind=component]
├── Icon
└── ValueText [可选 position_reference_id=Icon]
```

确实需要独立布局/交互尺寸、皮肤单独动画、裁切或动态内容排布等职责时，才在底板外增加纯结构根，并用 `ui_layout.independent_container_reason` 说明原因。若无底板，或该容器组织多个独立功能，也可按既有职责建立真实纯结构容器；不因“容器必须为空”或 Sprite 必须为叶子而拆分节点。

## 拆解记录

每个最终确认的 `decomposition_elements` 元素必须显式声明真实父归属及语义分类。以下例子中，文字实际属于购买按钮组件，定位时相对同级图标对齐：

```json
{
  "parent_element_id": "purchase-button",
  "semantic_grouping": {
    "kind": "part",
    "rationale": "该文字属于购买按钮功能组件，并按设计相对图标定位"
  },
  "ui_layout": {
    "grouping_basis": ["INTERACTION", "POSITION"],
    "position_reference_id": "purchase-icon"
  }
}
```

`parent_element_id` 必须引用同一 scene/state 的已声明真实容器，或稳定根 `viewport`/`safe-area`；它记录实际功能/布局归属，不承担独立定位参照的含义。`ui_layout.position_reference_id` 可省略；省略时使用 `parent_element_id`。显式参照必须满足同 scene/state、同坐标空间和无环规则。`semantic_grouping.rationale` 说明元素的功能归属、共同表达或实际父级职责；若定位参照独立于父级，也说明该位置关系。不得用“都是文字”“距离最近”“需要框住子项”作为分组或父级理由。

| kind | 含义 | 结构约束 |
| --- | --- | --- |
| `region` | 区域容器 | 容器，可组织组件、部件或独立元素；父级由真实职责决定。 |
| `component` | 功能组件容器 | 容器，可组合子组件或明确的空容器；父级由真实职责决定。 |
| `part` | 功能部件 | 叶子，可挂到任意已声明的真实容器或稳定根。 |
| `standalone` | 独立表达元素 | 叶子，可挂到任意已声明的真实容器或稳定根。 |

`kind` 只分类元素自身，不能限定其父级类别，也不能要求额外建立特定类型的中间容器。`region` 与 `component` 是容器，`part` 与 `standalone` 是叶子；所有父关系仍须指向真实容器或稳定根，并满足 scene/state、引用存在、自指与联合环检查。允许视觉溢出的子项按自身 bounds 验证，不扩大父框；空容器标记须与实际子项一致。

普通图片的原尺寸合同不由父子关系、参照关系、父容器 bounds 或布局策略覆盖。固定视觉图片必须以正式 SpriteFrame 的完整未裁切原尺寸使用 `SIMPLE + RAW`，`content_size` 为 `null`；运行时 `UITransform.contentSize` 仍等于该帧原尺寸。仅冻结九宫格的图片使用 `SLICED + CUSTOM` 和冻结目标尺寸。父级布局、Widget 或 Layout 不得向普通图片写入 `UITransform.contentSize`，也不得将普通图片标为 `STRETCH`/`FLEX`；经视觉合同批准的 Node 变换或反馈缩放动画不改变 RAW 内容尺寸，实际 bounds 另行验收。

九点停靠是位置关系：`axis_alignment.horizontal=left|center|right` 与 `vertical=top|center|bottom` 组合成九种语义，再以 `self_anchor`、`reference_anchor` 和 `offset` 表达。中心轴的 strict/reference 选择和组合成员规则见[居中策略与组合定位](center-alignment.md)。九点停靠与纹理切片合同 `nine_slice` 完全独立；九点停靠不触发 `CUSTOM`、切片或 RAW 尺寸修改。按预期的尺寸变化选择停靠语义，不按当前坐标落入几何九等分格来强推锚点；Node 的中心 `anchorPoint` 是另一个坐标转换属性。

## 阶段与校验边界

1. 阶段 A 先登记原子元素，再按功能归属与真实容器职责登记父子关系；有独立定位依赖时另记 `position_reference_id`。生成拆解图与技术 JSON。存在歧义就保留为待补充草案，展示争议点，不自动猜测或伪造人工决定。
2. 拆解人工确认覆盖分组种类、理由、实际父级、独立参照和显式溢出。缺少必需声明或结构不合法，不得通过最终确认或进入布局。
3. 阶段 B 按已确认元素原序把 `parent_element_id` 映射为 `parent_layout_node_id`，把有效定位参照映射为布局节点 `reference_id`，再做视觉双轴对齐判断和中心策略决策。输出节点、布局 PNG 与审阅资料需要同时保留实际父级和有效定位参照，可追溯到同一功能归属；只按明确中心策略派生布局 bounds，不回写拆解 proposal。
4. 机器检查字段完整、父容器引用、参照引用、同 scene/state 与坐标空间、父子边和定位参照边合并后的环、溢出声明、边界和确认身份一致性。机器不能从静态 bounds 证明功能归属或位置依赖正确；为满足类别或包含规则而包装、把共同功能拆成无关项、滥用 `standalone` 或填写无意义理由，仍由拆解人工审阅识别，不以 PASS 或 AI 自评代替确认。
5. 真实玩法、功能结构或视觉需求改变时，按既有阶段回到最早受影响的确认并更新下游身份。技术上合理的分组优化按既有确认流程更新受影响产物；不得把技术调整描述成用户未作出的决定，也不得伪造确认记录。

新增节点需要明确纳入既有拆解确认流程，已有元素相对顺序、身份和尺寸保持不变。布局节点的位置可按明确中心策略平移；proposal 中的原始 bounds 与确认回执不得被自动改写。
