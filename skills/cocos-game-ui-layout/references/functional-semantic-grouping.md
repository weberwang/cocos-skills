# 功能语义分组约束

适用于 V2 的效果图拆解与后置布局。先分别确认“位置依赖”和“信息分组”，再决定组件如何停靠；父子关系表达位置参照，分组表达共同信息，二者不得混用，也不得根据元素类型、所在大区域或最小包含矩形自动确定父级。

屏幕节点还须记录父容器职责、布局所有者、尺寸/溢出/安全区和输入策略。字段及 Cocos 根节点、空容器与 V1/V2/V3/V4 组织规则详见[Cocos UI 节点组织](layout-hierarchy.md)；`ui_layout` 不取代本文件定义的语义归属。

## 判断原则

- 全屏 UI 以场景逻辑尺寸为根参照；有底板弹窗以底板对应功能容器的尺寸为内容参照，底板容器本身相对场景定位；无底板弹窗以宿主场景逻辑尺寸为参照。先按[场景与弹窗尺寸参照](layout-hierarchy.md#场景与弹窗尺寸参照)确认边界，再建立内部位置依赖与信息分组；弹窗底板是功能部件，不是全屏背景。
- 父子关系由位置依赖决定：如果一个元素的位置、偏移或响应式移动依赖另一个元素，依赖方必须成为被依赖元素所对应布局容器的直接子元素。被依赖方不是容器时，先为它建立能代表该元素的显式 `component` 定位容器，再把依赖方放入其中；不得让二者继续平铺在区域或根下。
- 父容器 bounds 必须完整包含子项。角标等依赖项会突出被依赖元素边界时，不得伪造越界父子关系或修改原始元素 bounds；应新增经拆解确认的定位容器，以二者的联合范围作为容器 bounds，并让原始元素与突出项都归入该定位容器。这个容器代表被依赖元素的布局参照，不把二者误报成仅因共同信息而分组。
- 信息分组由表达目标决定：共同表达同一个信息或功能、但彼此没有位置依赖的元素必须归入同一个 `component` 容器，并作为同级子元素列出，不能任选其中一个充当另一个的父级。按钮的底板、图标、标题可以是独立元素，但应在同一信息组内。
- 同时存在信息归属和位置依赖时，两项都要保留：共同信息决定归入哪个组件组，组内的实际父子层级再按位置依赖建立；不能为了减少层级而抹平依赖关系。
- 区域容器组织多个功能组件。例如侧栏先包含多个入口组件，各入口再包含自己的图标与文字；不能把所有入口的图标、文字直接平铺在侧栏下，也不能建立仅按“所有文字”归类的容器。
- 原子资源身份与布局归属分离。不同入口可以复用同一图标资源，但每个可见实例仍属于自己的入口；不能仅凭相同资源 ID 合并容器。
- 不影响功能时，按[完整拆解与视觉显著性](../../cocos-game-asset-integration/references/asset-production-routes.md#完整拆解与视觉显著性)完整登记合成位图中可分离的文字、图标、底板、色彩填充等部件；系统文本和原生填充也保留为独立拆解项。拆开视觉来源不拆散功能归属，交互、状态联动、动态更新与本地化仍由对应组件协调。
- 几何包含、距离、视觉接近只用于辅助观察与验证。语义归属明确后才验证 bounds、计算偏移；没有声明父级时禁止自动选择最小包含容器。
- 独立标题、背景、装饰或不可可靠分离的完整品牌美术可以直接属于区域或根，不强制创建只有一个元素的容器；完整美术不能成为省略可独立部件的理由，整体保留时记录不可分离或分离会损伤既定视觉意图的原因。无需强制每个组件同时拥有图标、底板和文字。
- 空容器必须有已确认的用途与理由，不得把留白当作空容器。分组不得改变原图构图、元素位置、尺寸或已有元素顺序。

## 拆解记录

每个最终确认的 `decomposition_elements` 元素必须显式声明：

```json
{
  "parent_element_id": "entry-container",
  "semantic_grouping": {
    "kind": "part",
    "rationale": "该文字属于此入口，与入口图标共同移动并保持相对位置"
  }
}
```

`parent_element_id` 只能引用同一 scene/state 的已声明容器，或稳定根 `viewport` / `safe-area`。它表达确认后的位置依赖与布局归属，不包含停靠方向；最终确认不接受缺省父级。位置依赖存在时必须指向代表被依赖元素布局参照的直接父容器，没有位置依赖时才指向所属信息组、区域或稳定根。`semantic_grouping.rationale` 必须说明共同表达的信息、独立布局原因或该层级的位置依赖；不以“都是文字”“距离最近”作为分组或父级理由。

| kind | 元素类型 | 归属约束 |
| --- | --- | --- |
| `region` | 容器 | 组织区域、功能组件和独立元素；父级为区域或根 |
| `component` | 容器 | 表示一个功能组件，允许组合子组件或明确的空容器；父级为区域、功能组件或根 |
| `part` | 非容器 | 功能组件中的图标、底板、文字等部件；直接父级必须为 `component` 容器 |
| `standalone` | 非容器 | 有理由独立布局的标题、背景、装饰或整体美术；父级为区域或根 |

这里的 `kind=component` 表示功能组件容器，与拆解元素字段 `element_type=component` 表示非容器元素不是同一概念。复合功能可以嵌套组件，但区域不能塞入功能组件内部。所有显式父关系必须无环、不自指、几何可包含，且空容器标记与实际子项一致。

## 阶段与校验边界

1. 阶段 A 先登记原子元素，再按“位置依赖确定父子、共同信息确定同级分组”的顺序登记候选容器、归属和理由，生成拆解图与技术 JSON。存在歧义就保留为待补充草案，展示争议点，不自动猜测或伪造人工决定。
2. 拆解人工确认覆盖分组种类、理由与父级。缺少这些声明或结构不合法，不得通过最终确认或进入布局。
3. 阶段 B 按已确认元素原序把 `parent_element_id` 映射为 `parent_layout_node_id`，再做视觉双轴对齐判断。输出节点、布局 PNG 与审阅资料需要可追溯到同一功能归属；理由不能只存在于未绑定的旁注。
4. 机器检查字段完整、父级类别、引用、环、几何包含、跨组件归属与确认身份一致性。机器不能从静态 bounds 证明位置依赖或共同信息正确；把有位置依赖的元素平铺、把同一信息拆成无关项、把多个信息谎称为一个组件、滥用 `standalone` 或填写无意义理由，仍由拆解人工审阅识别，不以 PASS 或 AI 自评代替确认。
5. 新增容器、改变功能归属或分组理由，返回阶段 A 更新提案并重新确认，使旧拆解与布局身份失效。仅调整既有归属下的停靠与偏移，重新走布局确认，不自动重做参考图。

新增节点需要明确纳入新的拆解确认，已有元素相对顺序与原始 bounds 仍保持不变。该约束不授权自动改写已有项目的冻结工件或确认回执。
