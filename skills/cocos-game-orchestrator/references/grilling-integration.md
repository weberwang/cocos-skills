# 拷问与 F4 集成

总控先从用户请求、代码、配置、现有权威工件和确定性执行确认事实。只有无法确定且会改变产品范围、用户可见行为、视觉方向、预算、合规或数据边界的实质取舍才调用 `$grilling`。首次模块或边界变化不得机械触发。F4 只处理 A4 高影响集成与发布决定。

## 一般触发边界

1. 候选形成前先区分可探索事实与阻断候选的用户决定。前者继续探索；后者可直接 grilling，记录决策 ID、权威工件版本、范围、理由和失效条件，不虚构候选 SHA。
2. F0 处理任务范围与流程合规，F1 处理规格一致性，F2 处理专业质量，F3 处理工程验证，F4 只处理外部写入、付费、真机、破坏性或外部删除、发布等带副作用的 A4-A6；无副作用本地 A4 不经过额外批准门。
3. 新模块和模块边界变化仍按风险/变化执行模块审计、技术和 QA F2；若候选形成被实质架构决定阻断，可按第 1 条先 grilling；已有候选时则按第 2 条执行。证据完整且无用户决定时直接继续。
4. 未获结论前只冻结直接受影响范围，无依赖工作继续。结论绑定当前候选身份；修订候选只让覆盖事实变化的决定失效。

## 条件用户确认

- 已有明确需求或冻结基线，且候选不存在可见偏差或实质取舍：V1/V2 的额外产品取舍可记录 `AUTO`；这不替代全局选图、V2 拆解、独立布局或 Spine 批次人工确认，统一遵循[控制面不可绕过约束](../../cocos-game-workflow-control/SKILL.md#不可绕过约束)。
- 指定效果图忠实还原中，专业质量修复、工程适配或提升游戏感只有改变产品方向、玩法语义或上游结构时，才列出影响与候选方案并请求一次 `USER_DECISION`；默认 `usability` 下小幅位置、尺寸、边距和换行差异可直接修复并重验。
- 新方向、多种同等有效方案、用户可见结构/交互变化或高返工成本取舍：请求一次精确确认。
- G3 外部发布及受保护风险接受：按 A5/A6 显式批准。

不得无条件要求低保真与高保真两次批准。一次确认只覆盖所列取舍，不替代 V2 拆解/布局确认，也不豁免缺证与专业缺陷；外部动作仍按副作用单独批准。

## 记录

候选前决定记录决策 ID、权威工件版本、问题、影响、依据、推荐、用户结论、日期和失效条件；候选相关决定改为绑定候选身份。V1/V2 分别使用 `AUTO` 或 `USER_DECISION` 记录。旧候选选择、沉默、继续工作或参考输入不能替代当前选择。控制面仅索引决定，详细事实留在各自权威交付物，且不写 Approval Ledger。
